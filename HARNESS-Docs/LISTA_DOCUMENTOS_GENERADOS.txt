CONTENIDO EXTRAÍDO
================================================================================

✅ Los 4 Pilares del Harness
   └─ Repositorio = Sistema
   └─ Orquestación Multi-Agente
   └─ Spec Driven Development (SDD)
   └─ Supervisión Ejecutable

✅ Los 4 Agentes
   └─ Leader (Orquestador)
   └─ Spec Author (Diseñador)
   └─ Implementer (Constructor)
   └─ Reviewer (Inspector)

✅ 16 Archivos Obligatorios
   └─ 4 archivos base (CLAUDE.md, AGENTS.md, feature_list.json, init.sh)
   └─ 4 documentos (docs/architecture.md, conventions, specs, verification)
   └─ 5 archivos de agentes (.claude/agents/*.md + settings.json)
   └─ 2 archivos de estado (progress/current.md, history.md)
   └─ 1 archivo de criterios (CHECKPOINTS.md)

✅ El Flujo SDD Completo
   └─ pending → spec_ready → in_progress → done
   └─ Con puerta de aprobación humana entre spec_ready e in_progress

✅ EARS Notation (Especificaciones)
   └─ 5 patrones: Ubicuo, Evento, Estado, Opcional, No deseado
   └─ 3 archivos por feature: requirements, design, tasks

✅ Los 6 Checkpoints
   └─ C1: Arnés completo
   └─ C2: Estado coherente
   └─ C3: Código sano
   └─ C4: Verificación real
   └─ C5: Sesión cerrada
   └─ C6: SDD cumplido

✅ Trazabilidad Obligatoria
   └─ R<n> (requirements) ↔ test (verificación)
   └─ Cada R<n> debe tener al menos 1 test

✅ Reglas Duras (No Negociables)
   └─ Por cada rol (Leader, Spec Author, Implementer, Reviewer)
   └─ Prohibiciones explícitas y acciones obligatorias

✅ El Script init.sh
   └─ Verificación ejecutable (Python 3, archivos base, specs, tests)
   └─ Salida clara: [OK] o [FAIL]

✅ Ejemplos Reales (Ficticios pero Funcionales)
   └─ Flujo completo de un feature de CLI
   └─ Redacción de requirements en EARS
   └─ Implementación y verificación
